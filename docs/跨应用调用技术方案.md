# HMArkPriv 跨应用调用技术方案

> 目标：让其他 App 能像调用 Shizuku 那样，调用 HMArkPriv 执行特权 shell 命令。
> 调研环境：HarmonyOS NEXT 7.0.0.107 / API 26 / DevEco Studio SDK 26.0.0
> 日期：2026-11-04

---

## 一、先说结论：鸿蒙没有 Shizuku 的等价物

Shizuku 的模型是：**一个常驻进程暴露 Binder 接口 + 其他 App 通过 AIDL 绑定**，
Android 上有 `bindService` + `Service` 组件原生支持这种「无界面的跨进程服务」。

鸿蒙**不存在**这样的组件。逐一核实过 API：

| 组件 | 是否存在 | 能否做无界面服务 | 结论 |
|------|---------|----------------|------|
| `ServiceExtensionAbility` | ❌ 不在 API 26 导出列表 | — | 已废弃/未开放 |
| `AppServiceExtensionAbility` | ✅ 存在 | ✅ 能 | ❌ **仅 2-in-1 设备 + 需企业 ACL 权限**<br>`ohos.permission.SUPPORT_APP_SERVICE_EXTENSION` 只对企业应用开放 |
| `ActionExtensionAbility` | ✅ 存在 | ❌ 不能 | 继承 `UIExtensionAbility`，**是 UI 扩展**，会显示界面 |
| `ShareExtensionAbility` | ✅ 存在 | ❌ 不能 | 同上，用于接收分享内容 |
| `DataShareExtensionAbility` | ❌ 不在 API 26 导出列表 | — | 未开放 |

> 官方原文（`AppServiceExtensionAbility.d.ts`）：
> ```
> # Constraints
> - Currently, only 2-in-1 devices are supported.
> - To integrate an AppServiceExtensionAbility, applications must request the ACL permission
>   (ohos.permission.SUPPORT_APP_SERVICE_EXTENSION). This ACL permission is available only
>   for enterprise applications.
> ```

**所以普通个人开发者无法实现"其他 App 无感调用我的后台服务"。**
但有三条现实路径可以达到类似效果，代价各不相同。

## 二、四个可行方案

### 方案 A：Want 显式调用 · `startAbilityForResult`

**原理**：调用方用 `startAbilityForResult` 拉起我的 EntryAbility，
带自定义 action 和参数；我在 `onCreate`/`onNewWant` 里解析并执行，
完成后 `terminateSelfWithResult` 回传结果。

**已核实可用的 API**（`application/UIAbilityContext.d.ts`）：

```typescript
startAbilityForResult(want: Want, options?: StartOptions): Promise<AbilityResult>;  // L549
terminateSelfWithResult(parameter: AbilityResult): Promise<void>;                  // L372+
onNewWant(want: Want, launchParam: AbilityConstant.LaunchParam): void;             // UIAbility L578
```

`AbilityResult` 结构：
```typescript
interface AbilityResult {
  resultCode: number;
  want?: Want;    // want.parameters 可带任意数据
}
```

**调用方代码**：
```typescript
import { common, Want } from '@kit.AbilityKit';

const want: Want = {
  bundleName: 'com.octahedron.hmpriv',
  abilityName: 'EntryAbility',
  action: 'hmpriv.execute',              // 自定义 action 区分普通启动
  parameters: {
    cmd: 'id',
    timeoutMs: 5000,
  },
};

const ctx = getContext(this) as common.UIAbilityContext;
const result = await ctx.startAbilityForResult(want);
if (result.resultCode === 0) {
  const out = result.want?.parameters?.['output'] as string;
  console.info(`命令输出: ${out}`);
}
```

**我的 App 侧接收**（EntryAbility.ets）：
```typescript
onCreate(want: Want, launchParam: AbilityConstant.LaunchParam): void {
  this.handleExternalCall(want);
}

onNewWant(want: Want, launchParam: AbilityConstant.LaunchParam): void {
  this.handleExternalCall(want);
}

private async handleExternalCall(want: Want): Promise<void> {
  // 不是外部调用，走正常启动流程
  if (want.action !== 'hmpriv.execute') {
    return;
  }
  const cmd = want.parameters?.['cmd'] as string ?? '';
  const result = await this.busClient.execute(cmd);
  // 回传结果（参数只能放 Want.parameters，值需可序列化）
  this.context.terminateSelfWithResult({
    resultCode: result.success ? 0 : 1,
    want: {
      parameters: {
        output: result.output,
        exitCode: result.exitCode,
        durationMs: result.durationMs,
      },
    },
  });
}
```

| 维度 | 评价 |
|------|------|
| 能否拿回结果 | ✅ 能（`AbilityResult.want.parameters`） |
| 是否需要权限 | ❌ 不需要（靠 `exported: true` + 自定义 action） |
| 是否需要 App 常驻 | ❌ 不需要 |
| **缺点** | ⚠️ **会拉起 App 界面**，用户会看到画面一闪。可通过 `terminateSelfWithResult` 快速关闭，但仍有感知 |
| 参数限制 | 只能传可序列化数据（字符串/数字/布尔），大文本走参数会被截断 |

**适用场景**：低频、可以接受界面闪一下的调用。

### 方案 B：公共事件广播 · CommonEvent

**原理**：调用方发有序公共事件（ordered event），我订阅并处理，
用 `setCodeAndData` 把结果传给下一个订阅者/回传给发送方。

**已核实 API**（`@ohos.commonEventManager.d.ts`）：
```typescript
function publish(event: string, options: CommonEventPublishData): Promise<void>;   // L112
function subscribe(subscriber: CommonEventSubscriber, callback): void;             // L170
// 有序事件支持 setCodeAndData 回传（SDK 注释 L68）
```

**调用方**：
```typescript
import { commonEventManager } from '@kit.BasicServicesKit';

await commonEventManager.publish('hmpriv.execute', {
  parameters: { cmd: 'id' },
});
// 有序事件可用 setCodeAndData 拿回结果
```

**我的 App 侧**：
```typescript
const subscriber = await commonEventManager.createSubscriber({
  events: ['hmpriv.execute'],
});
commonEventManager.subscribe(subscriber, (err, data) => {
  const cmd = data.parameters?.['cmd'] as string;
  // 执行后 setCodeAndData 回传
  data.setCodeAndData(0, resultJson);
});
```

| 维度 | 评价 |
|------|------|
| 能否拿回结果 | ✅ 有序事件可以（`setCodeAndData`） |
| 是否需要 App 常驻 | ⚠️ **需要**。App 被系统回收后订阅失效，调用方发了没人收 |
| 参数限制 | 有大小限制（Intent 级别，通常几十 KB 内） |
| **缺点** | App 必须活着；广播是全局的，其他 App 也能监听（需约定校验字段防误触） |

**适用场景**：广播式通知（"所有监听者都执行某操作"），或配合方案 C 做通知。

### 方案 C：共享文件总线（**推荐**）

**原理**：复用现有的文件总线协议。其他 App 直接往 `Download/HMArkPriv/` 投递请求文件，
daemon 监听执行后回写结果，调用方轮询读取。

**为什么这个方案最好**：
1. **不依赖我的 App 活着** —— daemon 由 hdc 部署，独立运行，App 被杀也能工作
2. **无界面** —— 完全后台，符合 Shizuku 的"无感"体验
3. **数据量无限制** —— 文件读写，输出可以很大
4. **协议已存在** —— 现在 App 和 `hmpriv_cli.sh` 就在用，已被实测验证
5. **跨应用天然支持** —— `/storage/Users/currentUser/Download/HMArkPriv` 是所有 App 共享的用户目录视图

**关键：其他 App 能否访问这个目录？**

实测结论（见 `docs/Shell指令验证报告.md`）：
- App 用 `/storage/Users/currentUser/Download/HMArkPriv` 可直接访问（`accessSync` 返回 true）
- 该路径是**当前用户**的视图，所有 App 的 `currentUser` 指向同一真实目录
- 因此其他 App 只要具备 `READ_MEDIA`/`WRITE_MEDIA` 或用户授权，就能读写

**协议（完全复用现有）**：

```
Download/HMArkPriv/
├── cmd.req     # 调用方写：reqId|command\n
├── cmd.res     # daemon 写：ID:reqId RC:code TIME:ts\n<output>
└── status.json # daemon 心跳
```

**调用方代码**（可以封装成 SDK）：
```typescript
import { fileIo } from '@kit.CoreFileKit';

const BUS = '/storage/Users/currentUser/Download/HMArkPriv';

async function hmprivExec(cmd: string, timeoutMs = 5000): Promise<string> {
  const reqId = `ext_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`;

  // 1. 写请求
  const reqFile = fileIo.openSync(`${BUS}/cmd.req`, 0o2 | 0o100 | 0o1000);
  fileIo.writeSync(reqFile.fd, `${reqId}|${cmd}\n`);
  fileIo.fsyncSync(reqFile.fd);      // 必须 fsync，否则 daemon 可能读到空
  fileIo.closeSync(reqFile);

  // 2. 轮询结果
  const deadline = Date.now() + timeoutMs;
  while (Date.now() < deadline) {
    await new Promise<void>((r) => setTimeout(r, 50));
    const text = fileIo.readTextSync(`${BUS}/cmd.res`);
    if (text.startsWith(`ID:${reqId} `)) {
      return text.split('\n').slice(1).join('\n').trim();
    }
  }
  throw new Error('hmpriv timeout');
}
```

| 维度 | 评价 |
|------|------|
| 能否拿回结果 | ✅ 完整输出 |
| 是否需要 App 常驻 | ❌ 不需要（daemon 独立） |
| 是否需要我的 App 参与 | ❌ 不需要 |
| **缺点** | 调用方需要文件读写权限；需处理并发（多 App 同时写 reqId 冲突） |

**并发问题**：`cmd.req` 是单文件，多 App 同时写会互相覆盖。
解决：约定 reqId 带 App 标识前缀，或改用「请求目录 + 每请求一个文件」（见改进版）。

---

### 方案 C+：请求队列目录（推荐实现的版本）

改进方案 C 的并发问题：把单文件改成「请求目录 + 每个请求一个文件」。

```
Download/HMArkPriv/
├── req/                     # 请求队列
│   ├── ext_com.app.a_1700000001.req
│   └── ext_com.app.b_1700000002.req
├── res/                     # 结果目录
│   ├── ext_com.app.a_1700000001.res
│   └── ext_com.app.b_1700000002.res
└── status.json
```

**请求文件内容**：
```
<command>
```
**结果文件内容**：
```
RC:0
TIME:2026-11-04 12:00:00
<output>
```

调用方写完请求后轮询对应 `.res` 文件。daemon 处理完删除 `.req`。

优点：
- 天然支持并发（文件名即请求 ID）
- 调用方可以清理自己的结果文件
- 易于调试（能直接看到队列）

## 四、推荐路线

### 短期（最小可用）

用 **方案 C**（现有协议），因为：
- 代码零改动，协议已经在跑
- 其他 App 只要按格式写 `cmd.req` 就能用
- 只需对外发布一份「调用说明 + 示例代码」

**要做的事**：
1. 写一份 `docs/external-call-protocol.md` 给外部开发者看
2. 提供一个轻量 SDK（ArkTS 文件，直接拷进对方工程）

### 中期（体验优化）

用 **方案 C+**（队列目录）：
1. 改 daemon 支持 `req/` 目录扫描（兼容旧的 `cmd.req`）
2. 提供 SDK 封装

### 长期（如果要做完整生态）

- 方案 A 作为「快速调用入口」补充（适合一次性、可接受界面的场景）
- 方案 B 用于「事件通知」（如"命令执行完了"广播给多个监听者）
- 三者组合：C+ 为主，A 为辅，B 做通知

## 五、给外部开发者的接口定义（草案）

### 5.1 前置条件

```json
// 对方 App 的 module.json5 需要
"requestPermissions": [
  { "name": "ohos.permission.READ_MEDIA" },
  { "name": "ohos.permission.WRITE_MEDIA" }
]
```

首次调用时若目录不可访问，需要引导用户授权，或直接用 App 沙箱视图路径。

### 5.2 SDK 接口

```typescript
/** 执行特权 shell 命令 */
export function exec(cmd: string, options?: {
  timeoutMs?: number;   // 默认 5000
}): Promise<{
  success: boolean;
  exitCode: number;
  output: string;
  durationMs: number;
}>;

/** 检查 daemon 是否就绪 */
export function isReady(): Promise<boolean>;

/** 便捷方法 */
export const hmpriv = {
  exec,
  isReady,
  // 常用命令封装
  shell: (cmd: string) => exec(cmd),
  wakeup: () => exec('power-shell wakeup'),
  tap: (x: number, y: number) => exec(`uinput -T -c ${x} ${y}`),
};
```

### 5.3 错误码

| code | 含义 | 处理建议 |
|------|------|---------|
| 0 | 成功 | — |
| 1 | 命令执行失败（非 0 退出码） | 看 output |
| 1001 | daemon 未运行 | 提示用户部署 daemon |
| 1002 | 总线目录不可访问 | 引导授权 |
| 1003 | 超时 | 加大 timeoutMs 或检查命令是否阻塞 |

## 六、待决策事项

以下问题需要你确认后再动手实现：

1. **优先实现哪个方案？**
   - C（零改动，先能对外用）
   - C+（队列目录，解决并发）
   - A（Want 调用，最像"API 调用"但会闪界面）

2. **是否需要发布 SDK 包？**
   - 直接给源码文件（简单，对方拷过去）
   - 打包成 HAR（规范，但需要维护版本）

3. **是否要加调用方鉴权？**
   - 不加：任何 App 都能调（方便但危险 —— 任何 App 都能执行特权命令）
   - 加白名单：只允许指定 bundleName（更安全，需要在 daemon 侧校验调用方，但 daemon 是 shell 看不到调用方身份）
   - 加 token：调用方需先"申请"一个 token 写入约定文件（可实现，但增加复杂度）

   > ⚠️ **安全问题必须重视**：一旦开放跨应用调用，任何能写该目录的 App 都能执行任意 shell 命令
   > （包括 `rm -rf`、读取其他 App 数据等）。建议至少做 bundleName 白名单。

## 七、附：为什么不建议直接照搬 Shizuku

Shizuku 依赖 Android 的 `bindService` + AIDL，本质是**系统级 Binder 服务**。
它的前提是用户通过 adb 启动一个高权限进程（`sh /data/local/tmp/shizuku`），然后 App 绑定它。

鸿蒙上：
- ❌ 没有可被第三方 App 绑定的 Service 组件（除企业级 AppServiceExtensionAbility）
- ✅ 有 `hdc` + `shell(uid 2000)` 可以部署常驻进程 → 这正是我们 daemon 的方案
- ✅ 有跨应用共享的文件目录 → 这是我们的总线

**所以 HMArkPriv 的架构其实比 Shizuku 更简单**：
Shizuku 要靠 Binder + AIDL + 进程保活，我们靠文件 + daemon，同样能达到目的，
且没有 Binder 的版本兼容问题。

唯一的取舍是：文件轮询有 ~50ms 延迟（Shizuku 是毫秒级 IPC），
但对我们这些操作（点击、截图、改设置）完全够用。
