## 二、失败的部分：App 无法访问总线文件

### 2.1 现象

App 显示 `OFFLINE / Daemon 离线`，但 `status.json` 明确是 `ready`。

App 日志：

```
BusDirManager: probe: dir=/storage/Users/currentUser/Download/HMArkPriv  dirOk=true
BusDirManager: read fail: .../status.json code=13900002 No such file（首次，文件被我删了）
BusDirManager: read fail: .../cmd.res     code=13900001 Operation not permitted
```

**目录可访问（`dirOk=true`），但读文件被拒（`13900001`）。**

### 2.2 根因：Unix 权限 + SELinux 双重隔离

真机上总线文件的权限：

```
-rw-rw---- 1 20001006 file_manager   cmd.req
-rw-rw---- 1 20001006 file_manager   cmd.res
-rw-rw---- 1 20001006 file_manager   status.json
drwxrws--x 2 20001006 file_manager   .        ← 目录
```

| 主体 | 目录权限 | 文件权限 | 能力 |
|------|---------|---------|------|
| **App** (uid 20020256, 不在 file_manager 组) | other=`--x` 可遍历 | other=`---` 无权限 | ❌ 不能读、不能写、不能创建 |
| **shell** (uid 2000, 在 file_manager 组) | group=`rws` 可建/删 | group=`rw-` 可读写 | ⚠️ 能读写和删除**已存在**文件，但**不能创建**（SELinux 禁 hmdfs create） |

实测对照：

```bash
# shell 侧
mkdir $D/HMArkPriv/hmpriv_t   → MKDIR_OK      （目录已存在，-p 返回成功）
mkdir $D/testdir_859          → Permission denied   ← 真实创建被拒
touch $D/HMArkPriv/t.txt      → Permission denied   ← 创建文件被拒
echo x > $D/cmd.req           → WRITE_OK            ← 写已存在文件可以
rm -f $D/status.json          → RM_OK               ← 删除可以
chmod 666 $D/status.json      → Permission denied   ← 不是 owner，改不了权限

# App 侧
readTextSync(status.json)     → 13900001 Operation not permitted
openSync(..., CREATE)         → 13900001 Operation not permitted
```

**死锁形成**：App 创建不了文件（目录 other 无 w），也读不了已存在的文件（660）；shell 能读写但创建不了。没有任何一方的产物能被对方看到。

## 三、逐条排除的解决方案

### 3.1 READ_MEDIA / WRITE_MEDIA 权限 —— 无效 ❌

两个权限都是 `user_grant + normal`，普通 App 可申请，实测授予成功：

```
perm[0] ohos.permission.READ_MEDIA  = 0 (reason=0)   ← 授予成功
perm[1] ohos.permission.WRITE_MEDIA = 0 (reason=0)   ← 授予成功
```

但授予后：

```
read fail: .../cmd.res code=13900001 Operation not permitted   ← 依然读不了
openSync(..., CREATE) → 依然失败，无法创建文件
```

**结论**：媒体权限只管媒体库（图片/视频/音频），对 Download 下的普通文件（.json/.req/.res）无效。

### 3.2 READ_WRITE_DOWNLOAD_DIRECTORY —— 真机不支持 ❌

该权限在 `PermissionDefinitions.json` 里存在（`user_grant` / `normal` / since 11），但真机上申请返回：

```
perm[2] ohos.permission.READ_WRITE_DOWNLOAD_DIRECTORY = 2 (reason=0)
```

`2` = invalid request（无效请求）。模拟器上也是同样结果（`codes=[2] reasons=[0] dialogShown=[true]`）。

**结论**：该权限在 HarmonyOS 7.0.0.109 上实际不可申请。

### 3.3 App 沙箱目录 —— shell 进不去 ❌

```
ls /data/app/el2/100/base/com.octahedron.hmpriv/.../files   → 目录可见
touch .../files/probe.txt                                   → Permission denied
```

SELinux 隔离，shell 无法写入 App 沙箱。

### 3.4 自编译 socket daemon —— SELinux 禁执行 ❌

思路：绕开文件系统，App 连 `127.0.0.1:PORT`，daemon 用 C 写的 TCP 服务。

已完成的部分：
- 写了 `core/hmprivd.c`（~140 行，TCP 服务端 + popen 执行）
- 用 NDK 交叉编译成功：`aarch64-unknown-linux-ohos-clang` → 901 KB 静态二进制
- 验证 ELF 架构正确（`e_machine = 0xb7` AArch64，与手机 `arm64-v8a` 匹配）

失败点：

```bash
chmod 755 /data/local/tmp/hmpriv/hmprivd    → 成功
/data/local/tmp/hmpriv/hmprivd 19999        → Permission denied
```

文件权限 `-rwxr-xr-x`、SELinux 上下文 `u:object_r:data_local_tmp:s0`、`/data` 挂载无 `noexec`，
但**执行被拒** —— shell 域（`u:r:sh:s0`）被策略禁止执行 `data_local_tmp` 类型的 ELF。
换目录（`/data/local/tmp/hmprivd2`）同样失败。

> 这也解释了为什么 `sh /data/local/tmp/hmpriv/daemon.sh` 能跑而二进制不行：
> 脚本由已有的 `sh` 解释器执行，不涉及"执行新 ELF"。

附带发现：真机 toybox 极度裁剪，`nc` / `tr` / `awk` / `getconf` 都不存在，
手机侧也没有 python / node / perl / lua / busybox，无法用解释器实现 TCP 服务。

### 3.5 picker 目录授权 —— 无法完成选择 ❌

`DocumentViewPicker`（FOLDER 模式）在真机上能被拉起（`filePicker/NAPI` 有任务记录），
但和你之前反馈的一致：进入目标文件夹后没有"确认/完成"按钮，无法完成选择，
弹窗短暂出现后自行关闭。

| Socket 方案 | ❌ SELinux 禁执行自编译二进制 |

**根本矛盾**：HarmonyOS 7.0 在真机上对"普通 App"与"shell"做了严格隔离，
两者之间**不存在可共享的可写目录**。这不是代码问题，是系统安全模型决定的。

## 五、可行的解决方向

### 方向 A：让 App 放弃"直接执行"，改为"命令编辑器 + 结果查看器"

- App 负责编辑命令、保存历史、展示指令手册（这些已实现且完全可用）
- 命令的实际执行交给原方案：`hmshell`（在 Termux/MT 管理器里）或 HTML 控制台（浏览器）
- App 与执行端之间仍无法自动同步，需要用户手动复制粘贴

**优点**：立即能在真机用上一部分功能（指令手册、命令编辑）
**缺点**：不是"一键执行"，体验割裂

### 方向 B：改用系统级能力替代 shell

对我们需要的功能，很多有原生 API：

| 需求 | shell 方案 | 原生 API |
|------|-----------|---------|
| 电池信息 | `hidumper -s BatteryService` | `@ohos.batteryInfo` ✅ 已实现 |
| 屏幕常亮 | `power-shell timeout` | `@ohos.window.setWindowKeepScreenOn` |
| 截图 | `snapshot_display` | `@ohos.screenshot.capture` |
| 亮度 | `power-shell` | `@ohos.settings` / `@ohos.display` |
| 应用列表 | `bm dump -a` | `@ohos.bundle.bundleManager` |
| 启动应用 | `aa start` | `startAbility` |

**优点**：不依赖 shell，真机可靠
**缺点**：只能覆盖部分能力，`uinput`、`aa force-stop`、`param get` 等没有等价 API

### 方向 C：混合模式（推荐）

- **能用原生 API 的走 API**（电池、屏幕、截图、应用管理、系统参数）→ 真机可用
- **必须用 shell 的**（触控注入、强制停止等）→ 标注"仅模拟器/需配合 hmshell"
- App 内置 HTML 控制台的入口，一键在浏览器打开（浏览器有权限）

### 方向 D：继续深挖系统能力（不确定）

- 调研 `hdcd` 是否暴露可被 App 连接的本地端口
- 调研是否有 MDM / 企业应用通道可申请更高权限
- 关注鸿蒙后续版本是否放开 `READ_WRITE_DOWNLOAD_DIRECTORY`
