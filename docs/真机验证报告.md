## 二、关键结论：picker 授权 + 持久化，一次授权永久有效

### 2.0 授权持久化（最终方案，已验证）

**问题**：picker 返回的 URI 授权只在当前 App 进程有效。实测 App 重启后立刻变回
`13900001 Operation not permitted`，用户必须每次重新选目录。

**解法**：用 `@ohos.fileshare` 的持久化授权 API：

```typescript
import { fileShare } from '@kit.CoreFileKit';

// picker 拿到 URI 后立即固化
const policy: fileShare.PolicyInfo = {
  uri: uri,
  operationMode: fileShare.OperationMode.READ_MODE | fileShare.OperationMode.WRITE_MODE,
};
await fileShare.persistPermission([policy]);

// 每次启动时重新激活
await fileShare.activatePermission([policy]);
```

需要的权限：`ohos.permission.FILE_ACCESS_PERSIST`（`system_grant` + `normal`，**声明即得，无需用户弹窗**）。

**实测结果 —— 完全成功**：

```
15:12:27.222  activatePermission ok: file://docs/storage/Users/currentUser/Download/HMArkPriv
15:12:27.222  activate saved uri: true
15:12:27.223  read ok: /storage/Users/currentUser/Download/HMArkPriv/status.json (66 chars)
15:12:27.223  daemon alive: pid=20270 uid=2000
```

激活到读通仅 **1 毫秒**。之后每次重启 App 都自动连通，用户无需再操作。

### 2.0.1 修复启动时序误判

早期版本启动时会短暂显示"未授权"，原因是 `activatePermission` 生效有毫秒级延迟，
`canReadBus()` 首次调用失败就把 `needAuth` 置为 true 且不再回退。

修复内容：
- `initBusDir()` 中 `canReadBus` 加**重试**（5 次 × 120ms）
- `refreshDaemonStatus()` 改为**自愈**：即使 needAuth=true 也尝试检测，
  若读通则自动清除 needAuth
- 新增 `connecting` 状态，UI 显示「连接中」而非误导性的「未授权」

修复后启动日志（1ms 内完成，无中间状态）：

```
15:16:45.201  activate saved uri: true
15:16:45.202  daemon alive: pid=20270 uid=2000
```

## 二、关键结论：picker 授权是可行的

### 2.1 纠正早期误判

验证初期我遇到 `13900001 Operation not permitted`，一度判断"App 与 shell 之间无共享可写目录"，
**这是错的**。实际情况是：

- 我测试 picker 时没有走完完整的"选目录 → 确认"流程，误以为 picker 不可用
- 用户在真机上手动完成选择后，**授权立即生效**，App 之后可正常读写

### 2.2 授权机制的真实行为

从 App 日志可以看到完整的授权过程：

```
15:00:45.833  picked bus dir: file://docs/storage/Users/currentUser/Download/HMArkPriv
15:00:45.838  read fail: file://.../status.json  code=13900002 No such file or directory
15:00:45.857  write probe fail: ...（用 URI 拼路径写不进去）
15:00:48.581  read ok: /storage/Users/currentUser/Download/HMArkPriv/status.json (66 chars)  ← 成功
```

**关键发现**：

1. picker 返回的是 **URI**（`file://docs/storage/Users/currentUser/Download/HMArkPriv`）
2. **不能用 URI 直接字符串拼接来访问子文件**（会报 13900002）
3. 但 picker 授权后，App 获得了该目录的**访问许可**，
   之后用**绝对路径**（`/storage/Users/currentUser/Download/HMArkPriv/status.json`）读写都正常

这是鸿蒙 `fileAccess` 服务的机制：picker 给的是"目录访问凭证"，
持证后该目录下的文件操作被放行，与 Unix 660 权限无关。

### 2.3 实测命令执行

授权后点「应用列表」按钮：

```
BusClient: execute: reqId=req_1793775741163_0 cmd="bm dump -a"
BusClient: response: rc=0 time=2026-11-04 15:02:21 dur=307ms
界面显示：已装应用：共 224 个（解析成功）
```

**307ms 完成一次完整往返**（App 写 cmd.req → daemon 执行 → App 读 cmd.res → 解析渲染）。

界面状态也从 `OFFLINE` 变为：

```
UID:2000
Daemon 在线
PID: 20270  UID: 2000
```

且每 5 秒的轮询正常（`daemon alive: pid=20270 uid=2000` 持续输出）。

## 三、真机的权限模型（仍然值得了解）

虽然 picker 解决了问题，但真机的权限细节对理解边界有帮助。

### 3.1 文件权限

```
-rw-rw---- 1 20001006 file_manager   cmd.req / cmd.res / status.json
drwxrws--x 2 20001006 file_manager   .（总线目录）
```

| 主体 | 目录 | 文件 | 未授权时的能力 |
|------|------|------|--------------|
| App（uid 20020256） | other=`--x` 可遍历 | other=`---` | ❌ 不能读、写、创建 |
| shell（uid 2000，在 file_manager 组） | group=`rws` | group=`rw-` | ⚠️ 可读写删除**已存在**文件，但创建被 SELinux 阻止 |

所以**未授权时** App 确实访问不了；**picker 授权后**才突破这个限制。

### 3.2 shell 侧的真实限制

```bash
mkdir $D/testdir_859      → Permission denied   ← 不能在 Download 下创建目录
touch $D/HMArkPriv/t.txt  → Permission denied   ← 不能创建文件
echo x > $D/cmd.req       → WRITE_OK            ← 写已存在文件可以
rm -f $D/status.json      → RM_OK               ← 删除可以
chmod 666 $D/status.json  → Permission denied   ← 不是 owner 改不了权限
```

**这意味着总线文件必须预先存在**。实践中由 hdc 预创建（hdc 权限高于 shell），
或用原方案的 `install_and_start.sh` 部署。

## 四、逐条排除的方案（保留记录）

这些方案在本次验证中试过，都不如 picker 直接：

### 4.1 READ_MEDIA / WRITE_MEDIA — 授予成功但不足

```
perm[0] ohos.permission.READ_MEDIA  = 0 (reason=0)   ← 授予成功
perm[1] ohos.permission.WRITE_MEDIA = 0 (reason=0)   ← 授予成功
```

但仅这两个权限**不足以**读写 Download 下的普通文件（仍报 13900001）。
它们需要和 picker 授权配合，或者单独授予没有效果。

### 4.2 READ_WRITE_DOWNLOAD_DIRECTORY — 该版本不支持

```
perm[2] ohos.permission.READ_WRITE_DOWNLOAD_DIRECTORY = 2 (reason=0)
```

`2` = invalid request。该权限在 7.0.0.109 上实际不可申请（模拟器同样返回 2）。

### 4.3 自编译 socket daemon — SELinux 禁执行

思路：绕开文件系统，App 连 `127.0.0.1:PORT`。

已完成：`core/hmprivd.c`（TCP 服务端 + popen 执行），
用 NDK 交叉编译成功（`aarch64-unknown-linux-ohos-clang`，901KB 静态，ELF 架构验证正确）。

失败点：

```bash
chmod 755 /data/local/tmp/hmpriv/hmprivd  → 成功
/data/local/tmp/hmpriv/hmprivd 19999      → Permission denied
```

文件权限 `-rwxr-xr-x`、上下文 `u:object_r:data_local_tmp:s0`、`/data` 无 `noexec`，
但 shell 域被策略禁止执行该类型的 ELF。换目录同样失败。

> 这解释了为什么 `sh daemon.sh` 能跑：脚本由已有 `sh` 解释器执行，不涉及执行新 ELF。

**结论**：socket 方案在当前系统上不可行。源码保留在 `core/hmprivd.c` 供参考。

### 4.4 App 沙箱 — shell 进不去

```
touch /data/app/el2/100/base/com.octahedron.hmpriv/haps/entry/files/probe.txt  → Permission denied
```

SELinux 隔离，shell 无法写入 App 沙箱。

## 五、使用步骤（真机，已验证）

```bash
# 1. 部署 daemon（一次性，注意 LF 换行）
tr -d '\r' < core/daemon.sh > daemon_lf.sh
hdc file send daemon_lf.sh /data/local/tmp/hmpriv/daemon.sh
hdc shell "nohup sh /data/local/tmp/hmpriv/daemon.sh >/dev/null 2>&1 < /dev/null &"

# 2. 确认 daemon 就绪
hdc shell "cat /storage/media/100/local/files/Docs/Download/HMArkPriv/status.json"

# 5. 若状态未刷新，点状态卡片的 ↻ 刷新

```

## 六、已知问题与改进项

### 6.1 代码需要改进的地方

授权流程里 `pickBusDir()` 返回 URI，当前代码直接 `setBusDir(uri)` 并用 URI 拼接文件路径，
实测**会失败**（13900002）。正确做法是：

```
picker 授权成功 → 忽略返回的 URI →
重新用 findAccessibleBusDir() 探测绝对路径 →
用绝对路径作为 busDir
```

用户看到的"点确认后刷新才生效"，本质上就是这个原因：
第一次授权的 URI 路径不可用，刷新后重新探测到绝对路径才成功。

### 6.2 真机 toybox 极度裁剪

`nc` / `tr` / `awk` / `getconf` 都不存在，也没有 python / node / perl / lua / busybox。
（模拟器有 `tr`，真机没有）

影响：
- `arkui-app/scripts/verify-all.sh` 在真机上跑会有部分失败（依赖 `tr`、`awk`）
- 无法用解释器实现任何网络服务

### 6.3 总线文件需预创建

shell 不能创建文件，所以 `cmd.req` / `cmd.res` / `status.json` 必须由 hdc 预创建。
建议在 `install_and_start.sh` 里加一步，或用 App 首次 picker 授权后自己创建
（授权后 App 有写权限，可以创建 —— 这一点逻辑上成立，待验证）。
